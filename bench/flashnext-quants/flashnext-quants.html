Why: an “A6B” model was moving 11 GB per token

The experts are quantized properly and cost almost nothing. The dense parameters — attention, GDN projections, lm_head, shared expert — are read in full on every token, and most checkpoints leave them in BF16. They are 79% of the bytes and 67% of the parameters.

RadixArk (dense BF16) 10.98 GB
lovedheart (attn+GDN FP8) 7.25 GB
+ lm_head FP8 (ours) 6.61 GB
if all dense were FP8 5.44 GB
dense, BF16dense, FP8 active experts, NVFP4

At GB10’s 273 GB/s these set a floor of 40.2, 26.6 and 24.2 ms per token respectively. Three groups are not per-token reads and must be excluded from this arithmetic: the vision tower, embed_tokens, and the MTP drafter. We over-counted our own roofline by including them.

Why nobody had quantized lm_head

It is BF16 in every published GPU checkpoint. Not because it is unsafe — we measured +11% at no quality cost — but because three independent pieces of vLLM plumbing block it, and any one alone is sufficient.

1 The model never passes quant_config to ParallelLMHead So UnquantizedEmbeddingMethod is installed unconditionally and the checkpoint’s declaration is never consulted.
2 config.json is authoritative, and its ignore list contains lm_head Editing hf_quant_config.json — the obvious file — changes nothing. The field you read for placement is the field you must write.
3 The vocab loader asserts every tensor is vocab-shaped assert loaded_weight.shape[output_dim] == self.org_vocab_size is true of the weight and false of its [1940, 20] block-scale companion.

Does a quantization lever compose with speculation?

It depends on where the layer sits relative to the speculative loop — and we got this wrong at first, publishing a flat “they are substitutes”.

LeverMTP gain at c=1MTP gain at c=16Why
dense projections → FP8+67% → +23% +2% → −6% read once per step — both amortize the same read, so they compete
lm_head → FP8+23% → +40% −10% → +8% evaluated once per draft token plus verify — ~3× per step at k=2, so they compound

Acceptance is unchanged across both (mean accepted length 2.15 → 2.21), so this is pure speed rather than better drafting. Quantizing the head flipped speculation from a net loss at high concurrency to a net gain.

Do not use the published metrics files to compare checkpoints

gsm8k_metrics.json and aime26_metrics.json are byte-identical (sha256 88766f7e…, same latency_seconds to ten decimals) across a plain NVFP4 build, an FP8 dense-quantized fork of it, and a 512→448 expert-pruned variant. The model field inside names the original build. Hash them before letting them inform a decision — we repeated those figures ourselves before checking.

Two environment variables, both mandatory, neither documented

A VLLM_USE_DEEP_GEMM=0 DeepGEMM’s gate accepts the whole 120 capability family, which sm_121 satisfies — so vLLM routes blockwise FP8 to a kernel that then faults with CUDA error: unspecified launch failure during the startup profile run. Falls back to Cutlass and works. vllm#54125
B VLLM_GDN_DECODE_KERNEL=triton With FP8 GDN projections the default CUDA kernel hangs the engine at concurrency ≈32 — no error, requests simply stall.

Both are reachable only through blockwise-FP8 weights, so they appear exactly when you adopt the checkpoint class that helps most.

Measured on one NVIDIA GB10 (DGX Spark, sm_121, 128 GB unified), vLLM 0.1.dev20073+g8e685d198, PLE CPU offload, 8192 ctx, no speculation unless stated. Decode is clock-sensitive on this hardware — GB10 parks bandwidth-bound decode at ~82% of max SM clock (2411–2522 against 3003 MHz) and locking does not move it, so absolute figures are not comparable across projects.
