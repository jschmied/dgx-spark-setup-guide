TL;DR
  • Raised the concurrency cap --max-num-seqs 4 → 12 and --max-num-batched-tokens 8192 → 16384. Applied live (195 s cold start) and documented.
  • Load-tested to 12 concurrent users: 0 queueing, 0 errors, 0 preemptions, KV at 15%. The config change is validated end-to-end.
  • The binding limit is admission + decode bandwidth, never memory. KV cache never exceeded ~20% in any test.
  • Footprint is a fixed ~70 GiB regardless of user count — vLLM pre-allocates. 12 users add zero VRAM.
  • 8 developers @ 25% duty cycle fit comfortably. The only overload risk is 3+ simultaneous heavy agent fan-outs.
  • Best hardware upgrade keeping the exact NVFP4/vLLM stack: RTX PRO 5000 Blackwell (72 GB ~$6.3k, or 48 GB ~$4.2k).

1  Configuration change

The Spark serves one model at a time (llama.cpp router ⇄ vLLM, mutually exclusive). The vLLM launch caps were tuned for a single interactive user; they throttled a shared developer fleet at the admission layer long before memory.

FlagWasNowRationale
--max-num-seqs412Concurrency admission cap. KV pool supports ~13.3 full-context sequences; 4 was <⅓ of what memory allows.
--max-num-batched-tokens819216384Clears large agentic prefills (p95 ~134K tokens) in fewer scheduler steps under contention.

Raising the seq cap costs no extra memory — the KV pool is pre-allocated inside the --gpu-memory-utilization 0.4 budget; a higher cap simply admits more of it. Applied to /usr/local/bin/vllm-launch, documented in appendix/vllm-switch.md, service restarted (idle window, no requests dropped). Verified on the running process.

Finish-reason note (why length, not stop)

During the tests the finish-reason panel read 100% length. This is a test artifact, not a fleet-health signal: the driver capped max_tokens=400, right at real traffic's average generation length, so the open-ended "summarize + refactor" task truncated. A clean probe confirmed the engine emits stop correctly (finished naturally at 191 / 280 tokens with headroom). The request_success_total counter also reset on the restart, so this window contained only synthetic traffic. In production: if length ever dominates on real traffic, that's clients' max_tokens too low or runaway generation — worth an alert.

4  Memory / VRAM analysis

vLLM pre-allocates its entire footprint at startup. Concurrency scales KV usage, not allocation — 1 user and 12 users cost the same VRAM.

ComponentSizeScales with users?
Model weights (NVFP4)22.0 GiBNo — fixed (23.4 GB safetensors on disk)
CUDA graphs + activations~7 GiBNo — sized by max-num-batched-tokens
KV cache pool41.3 GiBNo — pre-reserved (= 3,487,654 tokens)
Total resident~70 GiBFlat (nvidia-smi: 71,512 MiB)

Per-token KV cost ≈ 11.8 KB (fp8). Per concurrent user: ~0.57 GiB at real 48K context, ~3.1 GiB at max 262K. Worst case — 12 users all pinned at full 262K context — needs weights 22 + KV ~35 + activations 7 ≈ ~64 GiB, which fits inside the 41.3 GiB KV pool with margin.

KV cache never exceeded ~20% in any test (6.6% historic, 10.5% at 8 users, 14.6% at 12). The pool is sized for long-context worst-case (max_concurrency 13.30× at 262K), and the "idle" ~35 GiB isn't wasted — with prefix caching on, freed blocks are retained and reused, driving the 80–95% hit rate. Memory is nowhere near a constraint; the wall is ~13 full-context sequences (admission), not GiB. This is unified LPDDR5X carved from the shared 128 GB pool, which is why --gpu-memory-utilization is a conservative 0.4.

Verdict: comfortable for interactive and light-agentic use — offered load sits at 2–4, peaks ~6, well inside 12. The swing factor is agent fan-out, not headcount: one dev's 5-way fan-out is fine; the only overload is 3+ heavy fan-outs landing together (statistically uncommon at 25% duty). When it happens you get brief waiting>0 and stretched E2E — not errors (KV has 6× headroom).

Two hard ceilings: aggregate throughput ~250 tok/s (sustained bandwidth limit — heavy parallel generation makes every token slower before anything queues), and admission at 12 (KV could support ~13 full-context / ~70 at typical sizes).

Recommendations: keep max-num-seqs=12 — well-matched. Guard against one runaway agent swarm filling all slots (cap per-session parallelism client-side, or a small proxy enforcing per-API-key concurrency; vLLM's cap is global only). Measure with the new Admission panel over a real week before changing anything.
